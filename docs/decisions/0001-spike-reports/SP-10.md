# SP-10: `RunControl` drain and resume in another process

Scripts: `spikes/sp10_graphs.py`, `spikes/sp10_resume.py`, `spikes/test_sp10_drain.py` (6 checks, all pass). Steps take 50 ms. Every step execution is traced to a file shared by both processes, so repeated work shows.

| Case (`durability="exit"`) | Result |
|---|---|
| Drain during a root-level chain | `GraphDrained("shutdown")` at the next superstep boundary (49 ms, the step in progress finishes). One root checkpoint; the new process continues; **no step repeated**. |
| Drain while two parallel nodes are in flight | Both finish, then the run stops; the new process runs the join; no step repeated |
| Drain while a child graph invoked in a node is running | The child inherits the `RunControl` and stops at its own boundary, **but its checkpoint is not saved** (0 checkpoints in its namespace). On resume the node re-runs and the child starts over: `c1` and `c2` ran twice. |

The child case under each durability mode (`test_child_drain_by_durability`):

| `durability` | Child checkpoints at drain | Repeated on resume |
|---|---|---|
| `exit` | 0 | `c1`, `c2` |
| `async` | 4 | none |
| `sync` | 4 | none |

(SP-2 showed that `exit` does save the child's checkpoint at an **interrupt**; the gap is specific to drains.)

**Conclusion:** drain-and-resume works, with one condition. Under `durability="exit"`, work done inside a child graph since the node started is lost on drain and repeated on resume. Only async runs resume after a drain (`runs.onInstanceLoss`: stream and sync fail with `SHUTDOWN`). So async runs use `durability="async"`, with the TurnSaver keeping `state.checkpointsKeptPerNamespace` (2) checkpoints per namespace, at about 25 % more cost per superstep (SP-1: 254 µs against 203 µs). Stream and sync runs keep `exit`. The fallback (release and restart the turn) is not needed. The LangGraph behavior is worth reporting upstream; the runtime does not depend on it changing.
