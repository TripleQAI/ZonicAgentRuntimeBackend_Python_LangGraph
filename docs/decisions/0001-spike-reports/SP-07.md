# SP-7: `langchain.mcp.MCPAdapter` (beta) with an in-process FastMCP server

Script: `spikes/test_sp07_mcp.py` (5 checks, all pass). LangChain 1.4.7, FastMCP 4.1.3, mcp 2.3.0. Importing `langchain.mcp` emits `LangChainBetaWarning`.

| Question | Result |
|---|---|
| Adapted tools in `create_agent` | Work; results arrive as content blocks (`response_format="content_and_artifact"`) |
| Pooling | Each tool call enters `async with client` (reference-counted). Not held: 5 calls open 5 connections (2.8 ms/call in process). Held by the caller: 25 calls, 20 concurrent, share **1** connection (1.0 ms/call). |
| Session identity | `ctx.session_id` differs per request under this MCP version, so it cannot identify a connection |
| Tools changed mid-session | A tool registered after connecting is listed by `list_tools()` with the default cache mode and with `cache_mode="refresh"` |
| Cancellation | Cancelling the caller's task reaches the server tool as `CancelledError` within 16 ms; the held connection stays usable |
| Tool failure (`ToolError`) | Reaches the model as a `ToolMessage` with `status="error"` and the server's text |
| String targets | Must be `http(s)` URLs; the adapter refuses strings that would launch a local process |

**Conclusion:** the design holds. The runtime's MCP pool holds one entered `MCPAdapter` per server for the process lifetime and refreshes tool lists on its own schedule (`cache_mode="refresh"`), so per-call connections never happen. The adapter is beta, so it stays behind the MCP port with `langchain-mcp-adapters` as the fallback named in design 20.1. Not needed now.
