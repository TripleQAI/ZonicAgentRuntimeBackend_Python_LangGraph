# SP-8: resuming a subset of several pending interrupts

Script: `spikes/test_sp08_partial_resume.py` (2 checks, all pass). Two parallel branches pause in one superstep: one directly, one inside a child graph invoked in its node; a deferred join follows. Every step goes through a TurnSaver bundle export and import, as a real resume would.

| Question | Result |
|---|---|
| `Command(resume={id_a: "yes"})` with two pending | Branch a finishes. Branch b stays pending **with the same interrupt ID**. |
| State across the partial resume | Kept through the bundle round trip. The second resume (`{id_b: "no"}`) finishes the run; the deferred join runs once. |
| Re-execution | A node that is resumed runs again from the top: a ran 2 times. An unanswered node re-runs on every resume: b ran 3 times. |
| Plain `Command(resume="yes")` with two pending | `RuntimeError`: the interrupt ID must be given |

**Conclusion:** the design holds. `POST /runs/{id}/interrupts/{interruptId}` resumes with an ID-keyed map, one or several answers at a time, and the fallback (wait for all answers) is not needed. Two rules follow, both already in the design. The API always resumes by ID, never with a plain value. Code before `interrupt()` must be free of side effects, because it re-runs on every resume (DR-10: interrupt kinds bind only their prompt port before `interrupt()`).
