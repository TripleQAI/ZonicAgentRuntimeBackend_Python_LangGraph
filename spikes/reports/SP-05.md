# SP-5: `ChatBedrockConverse` under 150 concurrent streams

Script: `spikes/test_sp05_bedrock_concurrency.py`. A fake boto client streams with 300 ms to the first event and 20 events 20 ms apart (ideal 0.70 s per stream), so the cost of the blocking client shows without AWS.

`ChatBedrockConverse` (langchain-aws 1.9.0) implements only the synchronous `_stream`. `astream` falls back to `BaseChatModel._astream`, which runs every `next()` of the boto event stream on the **event loop's default executor**.

| Executor | 150 streams, wall time | Time to first token p50 / p95 | Worst loop lag |
|---|---|---|---|
| Default (`min(32, cpu + 4)` = 32 threads) | 3.41 s | 1.39 s / 1.62 s | 29 ms |
| 64 threads | 1.78 s | 0.67 s / 0.98 s | 15 ms |
| 160 threads | 0.89 s | 0.36 s / 0.36 s | 17 ms |
| Native async baseline (`ScriptedChatModel`, same latency) | 0.94 s | 0.32 s / 0.33 s | 15 ms |

All 150 streams start immediately in every case; with too few threads their chunks wait for a thread. botocore's default HTTP pool is `MAX_POOL_CONNECTIONS = 10`, which the fake cannot show and which caps a real client the same way.

**Conclusion:** usable with the bounded-executor fallback named in design 20.1. The model executor must be sized to the concurrent model streams (`runs.maxConcurrentRuns`), not to CPUs; `settings.models.executorThreads` is raised from 32 to 160. The Bedrock client needs `botocore.config.Config(max_pool_connections=...)` of the same size. A per-provider executor (design Section 11) needs a thin `ChatBedrockConverse` subclass in `ModelFactory`, because LangChain's fallback always uses the default executor. `AsyncAnthropicBedrock` (anthropic 1.17.0) is available as the async-native alternative if the P5 load test shows thread cost.
